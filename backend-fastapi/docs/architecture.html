Reforge Backend Anatomy

How a YouTube URL becomes timestamped keywords grouped into categories: the modules, the eleven-stage analysis pipeline, every LLM call, and what lands in Postgres along the way.

4HTTP endpoints
17modules in app/, ~4,700 lines
11Postgres tables, 3 Alembic migrations
2 + NLLM calls per run minimum (N = eligible topic chunks)

Overview

The backend is a single FastAPI process. There is no worker queue and no background job system: an analysis runs inside the HTTP request that started it, from transcript fetch to final JSON. The work is a chain of LLM calls, each one validated by Python code before its output is trusted, with Postgres recording every intermediate artifact.

The core idea is grounding. The transcript is split into numbered segments (S001, S002…). Every LLM call refers to transcript positions only through these labels, and the backend resolves those labels back to real segment rows and real timestamps. A keyword the model invents with a segment range outside its chunk is rejected, not repaired.

Stack: Python 3.12, FastAPI, SQLAlchemy 2 (async, psycopg 3), Alembic, httpx for all provider calls, youtube-transcript-api for captions. Docker Compose runs the API with Postgres 16 and Redis 7.

Request lifecycle

Every request passes the same outer layers before reaching a route.

  1. RequestBodyLimitMiddleware (raw ASGI). Only for POST /analyze and POST /youtube/transcript: buffers the body and returns 413 once it passes 1 MB, then replays the buffered messages to the app.
  2. request_logging middleware echoes x-request-id back and logs method, path, status.
  3. Dependency injection. get_db opens one AsyncSession per request. For /analyze the route then builds the whole object graph by hand, per request: 
    llm      = LlmClient(settings, app.state.http_client)
service  = AnalyzeService(
             TranscriptStore(db),
             llm,
             settings,
             ExplanationEnricher(llm, OpenAIWebSearchClient(settings, http_client), settings))
# AnalyzeService builds its own YoutubeTranscriptIngestionService(store, fetch_youtube_transcript)
    Every collaborator is passed in through a constructor, which is what lets the tests swap in fakes.
  4. Error handlers turn any AppError, validation error, HTTP error, or unexpected exception into the { "error": { "code", "message" } } envelope.

The /analyze pipeline

All of this is AnalyzeService.analyze() in analysis.py:53. Each step emits an SSE stage name (the blue chips; these are what the iOS progress UI reads) and updates a local failure_stage, so a failed run records exactly where it stopped.

  1. Parse request, open a run schemas.py:130 · llm.py:54

    parse_analyze_request enforces the field allowlist and normalizes targetLanguage. resolve_llm_options settles provider, model (default gpt-4o-mini for OpenAI), temperature (0.2) and max output tokens (3000). An analysis_runs row is inserted with status=running before anything else happens.

    startedanalysis_runsINVALID_REQUEST · INVALID_TYPE · INVALID_TARGET_LANGUAGE

  2. Fetch and sanitize the transcript youtube.py:48 · sanitizer.py:60

    YouTube: extract the video ID, list caption tracks, prefer a human-made one over auto-generated, fetch raw snippets (blocking call, run via asyncio.to_thread). The sanitizer drops noise like [Music] or (박수), squashes ㅋㅋㅋㅋ and !!!!, sorts by start time, and numbers snippets as CleanedSegment(sequence, start, end, raw_text, text). Manual text is split on sentences and newlines into pieces of at most 320 characters, each given a fake 1-second slot.

    fetching_transcriptsanitizing_transcripttranscript_readyINVALID_YOUTUBE_URL · TRANSCRIPT_UNAVAILABLE · TRANSCRIPT_FETCH_FAILED · SHORT_TRANSCRIPT (< 80 chars)

  3. Store transcript and stable segments store.py:59

    Upserts a sources row keyed on (provider, externalId) (the video ID, or segments-v2:<hash> for manual text), a transcripts row keyed on (sourceId, sha256 of text), and one transcript_segments row per segment. Segment IDs are deterministic: seg_ + the first 32 hex chars of sha256(hash | sequence | start | end | text). Re-analyzing the same video reuses the same rows. The run is linked to the transcript.

    creating_segmentssourcestranscriptstranscript_segments

  4. Topic chunking (LLM call 1) llm.py:104 · prompts.py:132

    All segments are rendered as S001 | 00:12 | text lines. The model returns only boundaries: {startSegmentId, endSegmentId, title, summary, signalLevel}, where signalLevel is high, medium, low or off_topic. No retry: a malformed answer fails the run.

    chunking_topicstopic_chunking schemaLLM_TOPIC_CHUNKS_EMPTY · LLM_TOPIC_CHUNKS_INVALID_JSON

  5. Validate and repair chunk boundaries analysis.py:506

    Labels like S007 are mapped back to real segment IDs. build_topic_chunks then fixes what the model got slightly wrong, and records each fix as a coverage_warnings row: a reversed range is swapped; a chunk fully inside an earlier one is dropped; a partial overlap is trimmed to start at the next uncovered segment; an uncovered gap longer than 30 s or 5 segments becomes a major_gap warning. An unknown segment ID is not repairable and fails the run.

    validating_chunkstopic_chunkscoverage_warningsLLM_TOPIC_CHUNKS_INVALID_BOUNDARY

  6. Candidate clipping extraction (LLM calls 2…N+1) analysis.py:114 · llm.py:123

    Only high and medium chunks are eligible. One call per chunk, at most 3 in flight (asyncio.Semaphore(3)); if any chunk fails, the remaining calls are cancelled so no further paid requests run. Each call sees only its chunk's segments and returns keyword candidates with a kind (topic, claim, mechanism, risk, trend, entity, example, question, contradiction), the explanation ladder, a signalLevel, and sourceRefs that must point inside the chunk. Invalid output is retried up to 3 times with the validation error and the previous answer appended. The backend then rebuilds each source ref from the real segments: timestamp, YouTube link with &t=…s, and up to 300 characters of grounded text. low-signal candidates are dropped here.

    extracting_clippingscandidate_clipping schema · ≤3 attemptsLLM_CLIPPINGS_INVALID_JSON · LLM_CLIPPINGS_INVALID_SOURCE_REF

  7. Exact-duplicate removal analysis.py:368

    Two candidates collapse only when the casefolded term and the primary source start/end segment are both identical. "Codex" at 0:46 and "Codex" at 12:10 stay as two keywords. Survivors get short temporary IDs K001, K002… for the next LLM call.

    deduplicating_occurrences

  8. Category grouping (LLM call N+2) llm.py:174 · prompts.py:195

    The model receives a compact list (keywordId, term, kind, brief, contextualExplanation, timestamp) and returns {categories: [{title, keywordIds}]}. The validator requires every ID exactly once, no unknown IDs, no empty categories, and unique titles of 2–80 characters. Up to 3 attempts, with the required ID list repeated in the correction prompt.

    grouping_keywordskeyword_category_grouping schema · ≤3 attemptsLLM_CATEGORY_GROUPING_INVALID_JSON

  9. Coverage review analysis.py:638

    An eligible chunk that produced zero keywords, or a broad chunk (over 180 s or over 20 segments) with fewer than 2, gets a weak_candidate_extraction warning. Every chunk's coverageStatus is set: weak_candidate_extraction, off_topic, low_signal, represented (medium) or covered (high).

    reviewing_coveragecoverage_warnings

  10. Explanation enrichment (optional) explanation_enrichment.py:54

    Runs once per topic chunk. When EXPLANATION_ENRICHMENT_ENABLED is false (the default) or the provider is not OpenAI, it returns the transcript-only level2/level3 unchanged and makes no calls. Details in Enrichment.

    enriching_explanationsplan · review · web_search · synthesis

  11. Persist the category graph, build the response store.py:162 · analysis.py:441

    One transaction writes candidate_clippings, candidate_external_sources, candidate_external_citations, keyword_categories and keyword_category_memberships, after checking again that every occurrence is assigned exactly once. Any failure rolls the whole graph back. The response is then assembled from the grouping and validated through the AnalyzeResult Pydantic model, the run is marked completed, and a completed event goes out.

    storing_analysiscompleted5 tables, single commitINVALID_CATEGORY_GRAPH

On failure at any step, the session is rolled back, the run row is re-attached and marked failed with failureStage, errorCode and safeErrorMessage. A client disconnect during streaming cancels the task and records ANALYSIS_CANCELLED. Rows committed by earlier steps (transcript, chunks, warnings) stay.

LLM layer

LlmClient._generate is the single choke point: every task builds a system/user prompt pair plus a JSON schema and dispatches by provider.

ProviderEndpointHow JSON is enforcedDefault model
openai/v1/responsesStrict json_schema output formatgpt-4o-mini
gemini…/models/{m}:generateContentresponseMimeType: application/json, schema not sentgemini-1.5-flash
claude/v1/messagesPrompt instructions onlyclaude-3-5-haiku-latest

Because only OpenAI gets schema enforcement, the Python validators are what actually keep the pipeline safe on every provider. parse_json_object strips code fences before parsing. OpenAI HTTP errors are mapped to LLM_AUTH_ERROR, LLM_QUOTA_OR_RATE_LIMIT, LLM_CONTEXT_LENGTH_EXCEEDED or LLM_REQUEST_FAILED.

The explanation ladder

Each keyword carries four explanations of increasing depth. explanation_validation.py checks them on every candidate and again on every enrichment rewrite.

Internal nameAPI fieldRule
briefbrief5–10 words (or 5–40 non-space characters for CJK text), shorter than simpleExplanation
simpleExplanationlevel1Exactly 1 sentence. Never changed by enrichment.
contextualExplanationlevel22–3 sentences, longer than level1, joined length ≤ 420 characters
detailedExplanationlevel33–5 sentences, longer than level2, joined length ≤ 700 characters

Also enforced: the three levels must differ from each other, and the term must be 2–60 characters and not end like a sentence. Models may return level2/level3 as arrays of single sentences; normalize_candidate_sentences joins them with spaces.

Enrichment

Optional stage that rewrites level2/level3 with cited outside facts when the transcript alone leaves a gap. Off by default, OpenAI only. Its rule is that it can only add: every failure falls back to the transcript-only text, and it never raises out of the pipeline except on cancellation.

Citation IDs are local to one keyword: C1 on one keyword and C1 on another are unrelated. The synthesis validator rejects citation IDs that are not in that keyword's evidence, any attempt to return level1, and any change to keywordId. Only sources that are actually cited are kept in externalSources. Transcript source/sources are never touched.

Data model

Postgres is the durable record. Everything except the reusable source/transcript/segment layer is scoped to one analysis_runs row, so two analyses of the same video produce two independent sets of chunks, keywords and categories over shared segments.

When things get committed

The store commits after almost every step rather than once at the end. In order: run row → source → transcript → segments → run linked to transcript → topic chunks → boundary warnings → coverage warnings → the whole category graph in one transaction → run marked completed. That is why a failed run still leaves its transcript, chunks and warnings behind for inspection, but never half a category graph. The unique constraint on keyword_category_memberships.candidateClippingId enforces "each keyword in exactly one category" at the database level too.

Migrations

0001_nest_schema_baseline recreates the schema from the earlier NestJS backend, 0002_add_keyword_categories adds categories and memberships, 0003_add_candidate_external_sources adds the two citation tables. The Docker image runs alembic upgrade head on every start.

Streaming and errors

The SSE path decouples the pipeline from the HTTP response with an asyncio.Queue. The pipeline never knows it is streaming; it only calls emit(event, payload).

Without SSE the route simply awaits service.analyze(body) and returns the same AnalyzeResult as plain JSON; errors become HTTP status codes with the envelope. With SSE the HTTP status is always 200 and errors arrive as an event: error frame, because the headers were already sent.

Observations

Things I noticed while reading the code that are easy to miss or differ from what CLAUDE.md says. These are notes, not changes; nothing was modified.

  • Redis is not used for caching or coordination. CLAUDE.md scopes it to "cache/coordination uses", but the only Redis call is the PING in /health (main.py:121). If Redis is down, /health reports ok: false even though analysis would work.
  • The 30-minute transcript TTL is only reported. expiresInSeconds: 1800 and expiresAt are returned, but GET /transcript/{id} never checks expiry and nothing deletes old rows.
  • eval_runs has no writer. The table and model exist; no code inserts into it.
  • The LLM sees raw caption snippets, not the sanitizer's 20–35 s groups. sanitize_transcript builds grouped S001 | time | text lines (llm_transcript_text), but the pipeline formats prompts from the per-snippet transcript_segments rows (analysis.py:88). The grouped text is only stored as transcripts.transcriptText. For long videos this means many short segments in the chunking prompt.
  • Schema enforcement differs by provider. Only OpenAI receives the JSON schema. Gemini and Claude rely on prompt instructions plus the Python validators and retries, so expect more retries and validation failures there.
  • Docs are behind the code. CLAUDE.md says no test targets exist, but tests/ has 14 pytest files. It also does not mention type: "manual" analysis or POST /youtube/transcript.
  • Long-running request. The whole analysis lives inside one HTTP request (shared httpx timeout 120 s per provider call). A reverse proxy in front needs a long read timeout, and X-Accel-Buffering: no is already set for nginx.
